# 音声ルーティングの計画

トラックごとに1音源という今の作りを、**オーディオトラック** (音源とエフェクトの
連なり) と**その間のルーティング**に置き換える計画。

**名前を分ける。** 打ち込み側の「トラック」(`sequencer::TrackInfo`) はそのまま。
音の側に新しく**オーディオトラック**を立て、MIDI トラックを**参照する**形にする。

## やりたいこと (出発点)

- 音源を別ウィンドウに分ける
- **オーディオトラック0 をマスター**とする。0 は**常に受け手**で、送り側にならない
- オーディオトラックは **16本固定** (0〜15)。増減はしない
- 接続は**自由**。送り先は0個でも複数でもよく、**0個なら鳴らない**
- オーディオトラックは子ウィンドウを持ち、**音源とエフェクトを上から順に**刺す
- オーディオトラックは MIDI トラック番号を持ち、書かれた MIDI を入力とする
- 再生時はルートを順に通り、オーディオトラック0 を出力する

## いま出来ないこと

やりたいことの多くは「作りを足す」だけで済むが、**3つは今の作りが正面から
邪魔をする**。ここを先に潰さないと着手できない。

### 1. エフェクトが刺さらない (最大の障壁)

**プラグインに音を入れる経路が無い。**

- `audio/buffers.rs:126` — 毎ブロック**入力バッファを 0 で埋めている**。
  CLAP のエフェクトを載せても無音が入ってくる
- `audio/mod.rs:237` — VST3 のホストを `.input_channels(0)` で作っている。
  入力ポートを持たない構成で起動しているので、エフェクトは繋がらない
- `TrackProcessor::process(&mut self, steady, mix)` が **「mix に足す」**形
  (`buffers.rs:195` の `mix_into`)。エフェクトは「入ってきた音を読んで、
  処理した音で置き換える」必要があり、**この署名では表せない**

つまり今のホストは**音源しか載せられない**。「エフェクタを上から順に刺す」は
機能追加ではなく、**オーディオ経路の作り直し**になる。

### 2. ミックスバッファが1本しかない

`StreamAudioProcessor` は全トラックを1つの `mix` へ足し込んでいる
(`audio/mod.rs:464-480`)。ルーティングは「トラックの出力を**別のトラックへ**
渡す」ことなので、**トラックごとに出力バッファを持つ**必要がある。

### 3. トラック番号が MIDI と音源で同一

`GuiMsg::NoteOn { track }` / `Transport::emit_track(index, ..)` /
`project.rs` の `plugins: Vec<Option<PluginEntry>>` — すべて**同じ番号**で
MIDI トラックと音源スロットを指している。オーディオトラックを分けると、
**この番号が2種類に割れる**。GUI からオーディオスレッドへのメッセージは
すべて宛先の付け替えが要る。

### おまけ: 検証用のエフェクトが無い

`test-plugin` は**入力ポート0・モノラル出力1本の音源** (`test-plugin/src/lib.rs:310`)。
**エフェクトを刺す経路を確かめられるプラグインが手元に無い。**
フェーズ0 として先に治具を作る (後述)。

## 確定させる仕様

| 項目 | 決め |
|---|---|
| 本数 | **16本固定** (0〜15)。増減なし。**添字がそのまま識別子** |
| 接続 | **自由**。送り先0個 (=鳴らない) も複数も許す |
| 接続の持ち方 | 2本の間の接続は**1本だけ**。向きを**両者に書く** |
| トラック0 | **常に受け手**。送り側にならない |
| 循環 | 上の2つで**2本の輪は塞がる**。**3本以上の輪は別途拒否**する (下記) |
| 順序決定 | **メインスレッドでトポロジカルソート**し、確定した計画を送る |
| MIDI 入力 | オーディオトラック → MIDI トラックは **多対1**。無し (バス) も可 |
| チェーン | 上から順。**入力ポートを持たないノードは、そこまでの音を捨てる** |
| チャンネル | **グラフの中は常に2ch**。デバイスへ落とすのは最後の1回だけ |
| 音量・パン | **オーディオトラックごとの属性**。チェーンの後、送りに入る前に掛かる |
| 送りの音量 | **送り1本ごとに持つ**。トラックの音量とは別に掛かる |
| バイパス | **ノードごとに持つ**。音を素通しする (無音にしない) |
| 遅延補償 | **やらない** (下記) |
| ミュート/ソロ | フェーズ3 までは MIDI 側のまま。オーディオ側はフェーズ4 |

### 16本固定にする

**識別子の問題が丸ごと消える。** 増減しないので添字はずれず、`AudioTrackId` の
ような型も、番号の振り直しも要らない。`[AudioTrack; 16]` を持ち、**添字が
そのままトラック番号**になる。

バッファも最初に全部確保する。16本 × 2048フレーム × 2ch × 4B で **256KiB**
しかないので、使っていないトラックのぶんを惜しむ意味がない。

打ち込み側のトラック数は**今まで通り制限しない**。**音を出せる系統が16まで**、
という非対称になる (影響は「保存形式」の項)。

### 接続先を必須にしない

**繋がっていないトラックは鳴らない。それを仕様とする。** 出力先を必須にすれば
「繋ぎ間違えても音は消えない」が、そのぶん**繋ぎ方の自由度が落ちる**ので取らない。

代わりに**画面で分かるようにする**。鳴らない状態は2通りあり、**どちらも赤枠**で示す。

- **トラック0 へ辿り着けないオーディオトラック。** 計画を組み立てた時点で
  判別できる (0 から辺を逆向きに辿るだけ)。送り先が空の場合もここに含まれる
- **どのオーディオトラックからも参照されていない打ち込みトラック。**
  音を出せる系統が16 までなのに打ち込みは無制限なので、**普通に起こりうる**

送り先はすべて同じ扱い (**加算コピー**)。「出力」と「センド」を区別しないので、
プリ/ポストフェーダーの別も無い。送りごとの音量はフェーズ4 で再考する。

### 接続を1本にし、向きを両者に書く

2本のトラックの間には**接続が1本しか無い**。`A → B` と `B → A` が同時に
存在できないので、**2本での輪 (`A → B → A`) は構造的に作れない**。

向きは両側に持つ。どちらのトラックの子ウィンドウからも「相手が送り側か
受け手か」が引けるようにするため。

**ただしファイルには片側だけ書く** (送り側の `sends` のみ)。両側を書くと
`A` は「→B」と言い、`B` は何も言っていない、という**矛盾したファイル**が
作れてしまう。読み込みのときに受け側を組み立てる。

### トラック0 を受け手に固定する

マスターから他へ送れないので、**0 を含む輪は作れない**。0 の出力が
そのまま最終出力になる、という関係も一意に決まる。

### 3本以上の輪は残るので、繋ぐ時点で拒否する

**上の2つでは足りない。** `A → B` `B → C` `C → A` は、どの2本を取っても
接続は1本・向きは1つ、トラック0 も通らない。それでも**輪になっている**。

```
1 → 2 → 3 → 1        ← 対の規則も 0 の規則も満たすが、循環
```

実行時に見つける形にすると、**オーディオスレッドで探索する**か、**1ブロック
遅らせて切る**かになる。前者はリアルタイム安全でなく、後者は「繋いだのに
音が変」という説明の付かない状態を生む。**繋ぐ操作を断るのがいちばん安い。**

**16ノードなので、判定は「繋ぐ前に、繋ぎ先から自分へ辿り着けるか」を深さ優先で
見るだけ**。最悪でも辺の数ぶんしか歩かない。**繋ぐ操作は人の手の速さでしか
起きない**ので、計算量を気にする場面ではない。

### グラフの中は常に2ch にする

今は**チャンネル変換が1回しか起きない**。`buffers.rs:160` の `muxed_output` が、
プラグインの出力をミックスへ足す**その一瞬**でデバイスのチャンネル数へ揃えている。

| プラグイン出力 | デバイス | やること |
|---|---|---|
| 1ch | 1ch | そのままコピー |
| n ch | 1ch | `mix_mono` で混ぜて落とす |
| 1ch | 2ch | `mono_to_multi` で L/R に複製 |
| n ch | 2ch | `mux` でインターリーブ |

**チェーンを入れると「ノードとノードの間」が生まれる。** そこを何ch で流すかを
決める必要がある。**中を2ch 固定にする** — どのノードも 2ch を受け取り 2ch を
出す。バッファが全部同じ形なので、送りのマージは足すだけで済み、上の変換表も
「n ch → 2ch」の側だけを使う形でそのまま生きる。

代償は、**チェーンの途中にモノラルのエフェクトがあると、そこでステレオ感が
潰れて戻らない**こと。実機の DAW も同じ挙動なので、ノードのチャンネル数を
画面に出して分かるようにする。

**固定先はデバイスではなく常に2ch。** デバイスのチャンネル数に合わせると、
モノラル出力の環境では**書き出しまでモノラルになる** (書き出しは
`engine.config` のチャンネル数を使っている)。内部を2ch に固定し、
**トラック0 からデバイスへ落とすのを最後の1回だけ**にすれば、グラフも
書き出しもデバイスに左右されない。

デバイスが2ch なら処理は今と変わらない。増えるのは最後の変換1回だけ。
**3ch 以上のデバイスは今も panic する** (`buffers.rs:38`)。今回も広げない。

### 音量・パン・送りの音量

**音量とパンはオーディオトラックごとの属性。** ノードの一種にはしない
(チェーンの中に紛れると「どこにあるか探す」ものになるため)。

掛かる順番:

```
チェーン (ノードを上から) → トラックの音量・パン → 送りごとの音量 → 相手へ加算
```

**トラックの音量は全部の送りに効き、送りの音量はその送りだけに効く。** 原音を
マスターへ、同じ音を控えめにリバーブのトラックへ、といった配り方ができる。

パンは **-3dB の定パワー** (中央で左右とも 1/√2)。左右に振ったときに音量が
変わって聞こえないため。値は内部で線形の係数で持ち、画面には dB とパン位置で出す。

### バイパス

ノードごとに持つ。**バイパス中は音を素通しする** — 無音にはしない。
音源 (入力ポートを持たないノード) をバイパスすると、そこまでの音がそのまま
通る。チェーンの先頭なら無音になる。

**処理そのものを飛ばす。** バイパス中も動かし続ける手もあるが、その形は
「聞こえないのに CPU を食う」ものになる。代わりに**戻した瞬間に内部状態が
古い**という代償がある (ディレイやリバーブは、戻した直後に溜まりが無い)。
比べるために外す使い方では、これで困らない。

### 遅延補償 (PDC) をやらない理由

今は `latency: 0` を決め打ちしている (`buffers.rs:134,147`)。チェーンと分岐が
入ると、**遅延の違う経路が混ざって位相がずれるのが聴こえる**ようになる
(特に、原音とエフェクトを別経路で通してから混ぜたとき)。

それでも**今回はやらない**。プラグインの申告する遅延を集めて経路ごとに
遅延線を挟む話で、ルーティング本体と同じくらいの規模がある。
**「ずれる」ことを分かったうえで先に送る**。

## 実行の形

### 計画をメインスレッドで作る

オーディオスレッドは**確保も探索もソートもしない**。メインスレッドで:

1. 各オーディオトラックへ入ってくる辺を集める
2. トポロジカルソートして処理順を決める
3. トラックごとに作業バッファの番号を割り当てる
4. 順序とノードの並びを1つの計画にまとめ、rtrb で送る

オーディオスレッドは受け取った計画を**上から実行するだけ**。今の
`GuiMsg::SetTrack` が処理器を1つ差し替えているのと同じ要領で、
**計画ごと差し替える**。

### バッファ

トラックごとに1本 (`block_frames × channels`)。送り先へのマージは加算。
**16本ぶんを最初に全部確保する** — 2048フレーム × 2ch × 4B で **256KiB**。
使っていないトラックのぶんを惜しむ理由がない。

### `process` の署名

```rust
/// buf を読み、処理した結果で buf を**置き換える**。
/// 入力ポートを持たないノード (音源) は buf の中身を無視して上書きする。
fn process(&mut self, steady: u64, buf: &mut [f32]) -> Result<(), ProcessError>;
```

足し込み (`mix_into`) は置き換え (`write_into`) になり、**加算はグラフ側が
持つ**。今の「トラックが mix に足す」形は、トラックが1段しかなく行き先も
1つしか無いから成り立っていた。

### 書き出しも同じ経路を通す

`offline::render` は**自前のループで全処理器を1つの mix に足している**
(`audio/offline.rs:166-173`)。ここを放置すると、**書き出しだけルーティングが
効かない**ものが出来上がる。

グラフの実行は `audio/graph.rs` に**1つだけ**置き、再生とオフラインの両方が
それを呼ぶ。フェーズ2 の時点でここを寄せる (後から寄せるのは高くつく)。

## データモデル (案)

```rust
/// オーディオトラックの本数。0 がマスター
pub const AUDIO_TRACKS: usize = 16;

pub struct AudioTrack {
    pub name: String,
    /// 上から順に通す。音源もエフェクトも同じ列に並ぶ
    pub nodes: Vec<Node>,
    /// MIDI をどのトラックから取るか。None は入力なし (バス用)
    pub midi_track: Option<usize>,
    /// チェーンの後に掛かる音量 (線形) とパン (-1.0 左 〜 1.0 右)。
    /// **すべての送りに効く**
    pub gain: f32,
    pub pan: f32,
    /// このトラックが送る先。空なら鳴らない。**トラック0 では常に空**
    pub sends: Vec<Send>,
    /// このトラックへ送ってくる相手。`sends` から組み立てる控えで、
    /// **保存はしない** (両方書くと矛盾したファイルが作れてしまう)
    pub sources: Vec<usize>,
}

pub struct Send {
    pub to: usize,
    /// この送りだけに掛かる音量 (線形)
    pub gain: f32,
}

pub struct Node {
    // 音源かエフェクトか (中身は既存の TrackProcessor 相当)
    // ...
    /// 処理を飛ばして音を素通しする
    pub bypassed: bool,
}
```

ノードの宛先は `NodeAddr { track: usize, index: usize }`。
`GuiMsg::ParamValue { track, id }` はこれを持つ形に変わる。

**MIDI トラック → オーディオトラックは1対多になりうる** (同じ打ち込みを
複数の音源で重ねる)。`Transport::emit_track` は MIDI トラック番号のままでよく、
**配り先の対応表**をグラフ側が持つ。

## 保存形式

version 3。`plugins: Vec<Option<PluginEntry>>` を `audio_tracks` (16件) に
置き換える。接続は**送り側の `sends` だけ**を書き、受け側は読み込みで組み立てる。

**v2 からの移行:** 音源が載っていたトラック `i` を、`midi_track: i` /
**マスターへの送り1本 (音量は等倍)** / `nodes: [その音源]` の
オーディオトラック `i + 1` にする。
マスター (0) を新しく足す。**v1 / v2 が開けることは既存のテストが守っている**
ので、移行そのもののテストを足す。

**16本に収まらない v2 がありうる。** 打ち込みのトラック数に上限は無いので、
**音源を16個以上載せたファイル**は移行しきれない。既存の「音源の復元に失敗した
トラックを列挙して知らせる」経路 (`main.rs` の `restore_plugins`) に乗せ、
**溢れたぶんを名指しで報告する**。黙って捨てない。

読み込みの検証 (`project.rs` の `validate`) に足すもの:

- 送り先の番号が 0〜15 の範囲にあること
- **トラック0 が送り先を持っていないこと**
- 同じ2本の間に**両向きの接続が無いこと**
- **輪になっていないこと** (深さ優先で1周)
- 音量が**有限で負でないこと**、パンが `-1.0..=1.0` に収まること。
  既存のノートと同じ理由で、**NaN を通すと以降の計算すべてに波及する**
  (`project.rs` の `non_finite_positions_are_rejected` と同じ扱い)

**ファイルから来た循環をそのまま実行させない。** 手で書き換えたファイルや、
将来の版で作ったファイルが入口になりうる。編集操作で拒否するだけでは塞がらない。

## フェーズ

各フェーズの終わりで**アプリが動く状態**を保つ。

### 0. 検証用のエフェクトを作る — **済 (2026-08-17)**

`test-plugin` にエフェクトを足した。1つの `.clap` に音源と2つ入っている。

| 索引 | ID | 中身 |
|---|---|---|
| 0 | `com.example.test-sine` | 従来の音源 (**索引は変えていない**) |
| 1 | `com.example.test-gain` | 入力1・出力1・モノラルの `out = in * gain + offset` |

**`gain` の既定は 0.5。** 等倍にすると「効いた」と「素通しだった」が区別できず、
バイパスの検証にならない。**`offset` は順序を見るためにある** — 掛け算だけだと
前後を入れ替えても結果が同じで、チェーンの順が守られているか分からない。

検証は `gain_smoke` (clack を直接叩いて入力バッファに既知の信号を置く。
**ホスト本体はまだエフェクトに音を入れられない**ため)。見るのは
「1ファイルから2つ見えること」「`in*gain+offset` になっていること」
「2段の順序を入れ替えると結果が変わること」の3つ。

CLAP なので **clap-wrapper で VST3 版も作れ**、両バックエンドの入力経路を
同じ治具で確かめられる (VST3 版はフェーズ1 で必要になったときに作る)。

1ファイルに2つ入れたのは、**ホスト側の「1ファイルに複数」の経路も一緒に
通せる**ため。索引0 を音源のままにしたので、既存の検証バイナリは影響を受けない
(`smoke` / `seq_smoke` / `choke_smoke` / `state_smoke` / `wav_smoke` で確認済み)。

### 1. エフェクトを刺せるようにする — **済 (2026-08-17)**

**ルーティングはまだ無い** (全トラックが今まで通り1つの mix へ足される)。
画面から作れるトラックも1段のまま。**チェーンを組めるのはまだ `chain_smoke`
のような検証経路だけ**で、画面から積めるようにするのはフェーズ4。

入れたもの:

- **入力バッファの供給。** `buffers.rs` に `demux` (インターリーブ →
  チャンネルごとの連続配置) を足し、`prepare_plugin_buffers` が
  **メイン入力ポートへ入ってきた音を書く**
- **`process` を「足し込み」から「置き換え」へ。** `mix_into` → `write_into`。
  渡されたバッファが入力と出力を兼ねる。**トラック同士を混ぜるのは呼び出し側**
- **トラックごとの作業バッファ。** 共有のミックスへ直接書かせると、前の
  トラックの音を次のトラックのエフェクトが拾う。再生 (`audio::mod`) と
  書き出し (`offline`) の両方に同じ形で入れた
- **`TrackProcessor` がノードの列を持つ。** 上から順に通す。音源かエフェクトかは
  区別せず、**入力ポートを持たないノードがそこまでの音を捨てる**のは上書きの結果
- **VST3 の `input_channels`。** `0` だと入力バスの無い音源専用の構成になる

#### パラメータに宛先が要ることが分かった

計画では見落としていた。**音符と CC はトラックの全ノードへ配ってよい**
(受け取れないノードは自分で捨てる) が、**パラメータは配ってはいけない**。
同じエフェクトを2段刺したとき、片方だけを動かせなくなる。

`BlockEvent::Param` に `node`、`GuiMsg::ParamValue` に `node` を足し、
各バックエンドが自分宛てだけを拾う。`chain_smoke` の3番目がこれを見ている
(全段に配ってしまうと基準比が 4.0 になるので、間違えれば必ず落ちる)。

#### 検証

`chain_smoke` で、音源だけの音量を基準にした比で見る。

| チェーン | 基準比 | 意味 |
|---|---|---|
| 音源 → ×0.5 | 0.500 | **エフェクトに音が入っている** |
| 音源 → ×0.5 → ×0.5 | 0.250 | 2段を順に通っている |
| 音源 → ×2.0 → ×0.5 | 1.000 | パラメータが段ごとに効いている |
| 音源 → 音源 | 1.000 | 入力を持たない段が前の音を捨てている |
| 音源 → ×0.5 (VST3) | 0.500 | **VST3 エフェクトにも音が入っている** |
| 音源 → ×0.5 (VST3) → ×0.5 | 0.250 | VST3 の出力を CLAP が受け取れている |

**VST3 は clap-wrapper で作った `test_plugin.vst3` で確認した** (作り方は
`guide.md`)。`test-plugin` の2つがそのまま2つの VST3 クラスになるので、
**同じ治具で両方のバックエンドを見られる**。

`input_channels` を 0 から変えた影響も確認済み。ラップした音源は
`AUDIO in: 0, out: 1` のままで、入力バスを用意しても音源側は変わらない。

#### 上書きへの変更で `mixed_smoke` が壊れていた

**実害が1件あった。** `mixed_smoke` の実時間側だけ、共有のミックスへ
全トラックを直接 `process` させる古い形が残っていた。上書きになった今は
**後のトラックが前のトラックを消す**ので、CLAP だけの区間が無音になっていた
(オフライン側は直してあったので、書き出しのピークは正しいままだった)。

VST3 が無くて回せていなかったぶんで、**実物を用意した時点で初めて出た**。
`audio::mod` / `offline` と同じ「作業バッファを通してから足す」形に直した。
`seq_smoke` / `choke_smoke` / `vst3_smoke` は1トラックなので影響なし
(毎ブロック 0 で埋めてから渡しており、新しい約束をそのまま満たしている)。

#### チャンネル幅はまだストリームのまま

「グラフの中は常に2ch」は**入れていない**。今はデバイスのチャンネル数
(`output_channel_count`) がそのままバスの幅になる。ノードとバスの間の変換は
入ったので、**幅を定数 2 に変えるのは残りの小さい差分**。バッファを組み直す
フェーズ2 で一緒に入れる。

### 2. オーディオトラックを分ける

`AudioTrack` 16本、トラックごとのバッファ、マスター0、全部がマスターへ直結。
`audio/graph.rs` を作り、**再生とオフラインの両方をそこへ寄せる**。
保存形式 v3 と移行。

### 3. ルーティング

送り先の編集、トポロジカルソート、循環検出 (編集時とファイル読み込み時の両方)。
検証は `route_smoke`。

### 4. UI

オーディオトラック一覧のウィンドウと、トラックごとの子ウィンドウ (縦の
チェーン)。ここで入れるもの:

- 音量・パン、送りごとの音量、ノードのバイパス
- オーディオトラック側のミュート/ソロ
- **鳴らないものへの赤枠** (オーディオトラックと打ち込みトラックの両方)
- ノードのチャンネル数の表示 (どこでステレオが潰れるかを見えるように)

## 決まっていないこと

- **オーディオ側のソロの意味**。バスへ送っているトラックをソロにしたとき、
  バスも聞こえるべきか (経路を辿って残すのか、そのトラックだけにするのか)
- **3ch 以上のオーディオデバイス**。今も panic するまま (`buffers.rs:38`)
- **遅延補償**。やらないと決めたが、いつか要る (上記)
