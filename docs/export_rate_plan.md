# Opus 書き出しの計画

WAV に加えて **Ogg/Opus** で書き出せるようにする。ビットレートは
**48 / 96 / 128 / 192 kbps** から選ぶ。

## 使うもの (どちらも純 Rust・C 不要)

| クレート | 用途 | ライセンス | 状況 |
|---|---|---|---|
| [opus-rs](https://crates.io/crates/opus_rs) | Opus の符号化 | BSD-3-Clause | 0.1.26 / 8.4万DL / 2026-08-05 更新 |
| [ogg](https://crates.io/crates/ogg) | Ogg 容器 | BSD-3-Clause | 0.9.2 / 890万DL |

**README で「libopus (C) の CMake が要るので見送り」と書いた理由は消えている。**
どちらも BSD-3-Clause なので、MIT のまま配布できる (表示義務が増えるだけ)。

`OpusEncoder` は必要なものが揃っている。

```rust
pub struct OpusEncoder { pub bitrate_bps: i32, pub use_cbr: bool, pub complexity: i32, .. }
pub fn new(sampling_rate: i32, channels: usize, application: Application) -> Result<Self, _>
pub fn encode(&mut self, input: &[f32], frame_size: usize, output: &mut [u8]) -> Result<usize, _>
```

**`encode` が f32 をそのまま取る**ので、`Rendered.samples` を変換せずに渡せる。

## 壁は2つだけ

### 1. `.opus` は Ogg 容器が要る

`opus-rs` が返すのは生の Opus パケット。再生できるファイルにするには Ogg で包み、
先頭に `OpusHead` と `OpusTags` の2ページを置く。`ogg` クレートで書けるが、
**ヘッダの中身 (プリスキップ・チャンネルマッピング・出力ゲイン) は自分で組み立てる**。
ここが唯一の未知数なので**フェーズ0で潰す**。

### 2. Opus は 48kHz でしか鳴らせない (このプロジェクトでは)

Opus が受け付けるのは 8 / 12 / 16 / 24 / 48 kHz。一方このアプリは
**「44.1kHz 以上で最小のレート」** を選ぶ作りなので (`config.rs` の `find_best`)、
一般的な Windows のデバイスでは **44.1kHz** になる。**48kHz を作る必要がある。**

やり方が3つあり、コストがかなり違う。

| 案 | 内容 | 代償 |
|---|---|---|
| **A. ストリーム自体を 48kHz にする** | `find_best` の選び方を「48kHz が使えるなら 48kHz」に変える | **一行で済み、再生も書き出しも 48kHz に揃う。** 48kHz を出せないデバイスでは結局 B か C が要る |
| **B. 書き出しのときだけ音源を 48kHz で回し直す** | 借りた音源を `reconfigure` / 再 `activate` して描画し、戻す | 最も正確だが、**戻せないとそのトラックが再生できなくなる** |
| **C. リサンプリング** | `rubato` で 44.1k→48k | 依存が1つ増える。音質の劣化はごく小さいが、ゼロではない |

### 決定: B (2026-08-12)

当初は A を勧めたが、**フェーズ0 で実機が 44.1kHz 固定だと分かった**（下記）。
A は「Windows のサウンド設定が 48kHz のときだけ成り立つ」ものになる。

**公開しているプロジェクトなので、動くかどうかを利用者の環境設定に依存させない。**
どの環境でも Opus を出せる B を採る。

代償は「戻せないとそのトラックが鳴らなくなる」危険で、そこは実装で受け止める
(下記「いちばん危ないのは戻すところ」)。

なお **A は同時に入れてよい**。ストリームを 48kHz にできる環境では切り替えが
不要になり、B の危険を通らずに済む。ただし本筋ではないので後回し。

## ビットレート

`bitrate_bps` に bps で入れる。UI では kbps で見せる。

| 選択肢 | 用途 |
|---|---|
| 48 kbps | かなり小さくしたいとき |
| **96 kbps** | **既定。** Opus の利点は低いビットレートでも音質が保たれることなので、そこを活かせる値にする |

### 高ビットレートは出さない (実測して決めた)

**`opus-rs` 0.1.26 は、内容によって壊れたストリームを吐く。** 192kbps で書き出した
ファイルにノイズが乗ることに気付いて調べた結果:

2種類の信号を書き出し、**本家 libopus (ffmpeg) で復号**して、**入力そのものと
スペクトルを突き合わせた**もの (数値が大きいほど元に近い)。

| 信号 | 48 | 96 | 128 | 160 | 176 | 192 |
|---|---|---|---|---|---|---|
| サイン波 | 26.3 | 30.6 | 34.1 | 35.9 | **5.0** | **2.7** |
| 和音+ノイズ | 10.5 | 11.9 | 12.3 | **5.1** | **5.0** | **4.8** |

**閾値は内容で変わる** — サイン波は 176kbps、和音+ノイズは **160kbps** で崩れる。
実際の曲は 192kbps で発覚した (それ以下は試していない)。**両方で正常だった上限は
128kbps。**

信号が違うと絶対値は比べられない (ノイズを含むほうは正常でも一致度が低い)。
見るべきは**変化**で、**ビットレートを上げたのに悪化するのは正常な符号化器では
あり得ない**。

聴感とも一致する。サイン波は 160 まで澄んだ音、176 以上はノイズ。和音+ノイズは
128 までは音程感があり、160 以上は「雨や水の音」のような音程感のないノイズになる。

#### 測定方法で二度つまずいた

**1. 「範囲外サンプル (|x|>1.0) の数」で測っていた。** これは**範囲内に収まった
まま中身が壊れる場合を取りこぼす**。実際、和音+ノイズは**完全に壊れていても
範囲外が0個**で、この指標では見逃していた。「複雑な信号なら高ビットレートでも
平気」という誤った結論を出しかけた原因がこれ。

**2. 古い `.opus` を聴いて誤った結論を出しかけた。** 検証用の bin を足したせいで
`cargo run` が失敗しており、ファイルが再生成されていなかった。複数回の実行
(途中で信号を変えている) の産物が混ざった状態で聴き比べていた。`default-run` を
指定して塞いである。

**どちらも耳で確かめて気付いた。** 指標を疑うときは聴くのが早い。

**閾値は内容で変わる。複雑な内容ほど安全、ではない** — むしろ和音+ノイズのほうが
サイン波より早く (160kbps で) 崩れた。`complexity` を 0 / 5 / 10 と変えても
改善しない。

つまり **ビットレートだけでは安全な線を引けない**。壊れたファイルが黙って
出来上がるのが最悪なので、**実測で問題の無かった範囲だけを出す**。

- 128kbps は手元の全ての信号で正常だったが、**内容次第という性質**は変わらないので
  余裕を取って外した
- 48 / 96 はいずれの信号でも正常。既定の 96 は、低ビットレートで音質が保たれる
  という Opus の利点にも合っている

**上流へ報告済み**: <https://github.com/restsend/opus-rs/issues/11>
(本文と再現手順は `spike/opus/upstream-issue.md` と同ディレクトリの検証コード)。
**クレートが直れば選択肢を増やせる**ので、反応があったら
`host/src/opus.rs` の `BITRATES_KBPS` を見直すこと。

可変ビットレート (VBR) が既定。`use_cbr` は触らない (配信ではないので、
指定した値に張り付かせる理由がない)。

## フェーズ0 の結果

`spike/opus/` に独立したクレートを置いて確かめた (親のワークスペースからは
切り離してある)。

### Ogg 容器は解決した。ただしプリスキップの勘定を最初は間違えた

**ヘッダの組み立て自体は素直だった。** `OpusHead` (19バイト) と `OpusTags` を
自前で作り、`ogg` クレートの `PacketWriter` に渡すだけ。

**間違えたのはグラニュール位置。** 最初は「入れた長さ + プリスキップ」を終端の
グラニュールに書いたが、**フレームを余分に出していなかった**ため、復号すると
2.000秒のはずが **1.9935秒 (96000 → 95688 サンプル)** になった。ちょうど
プリスキップ 312 サンプルぶん足りない。

符号化には先読みの遅れがあり、**復号側は頭から `PRE_SKIP` サンプルを捨てる**。
入れた音を最後まで取り出すには、**そのぶん余分に流し込んでフレームを1つ多く出す**
必要がある。直したところ、ffmpeg での復号が**ちょうど 96000 サンプル (2.000000秒)**
になった。

**検証は第三者の実装で行った。** 自前の復号器で往復させても、同じ勘違いをして
いれば通ってしまう。`ffprobe` / `ffmpeg` で確かめている。

```
ffprobe : codec_name=opus / sample_rate=48000 / channels=2 / bit_rate=128932
ffmpeg  : 復号すると 96000 サンプル = 2.000000 秒 (入れた長さと一致)
          mean_volume -9.0 dB / max_volume -5.3 dB (無音でない)
```

指定した 128000 bps に対して実測 128932 bps なので、**`bitrate_bps` は効いている**。

### 案 A の前提が崩れた。実機は 48kHz を出せない

```
デバイス: OUT 1-2 (2- BEHRINGER UMC 202HD 192k)
  2ch 44100..44100Hz U8 / I16 / I32 / F32
48kHz を出せるか: いいえ
```

**すべての構成が 44100..44100 で固定**。機材は 192kHz まで扱えるものなので、
これはハードウェアの制限ではなく **Windows のサウンド設定 (共有モードのミックス
形式)** が 44.1kHz になっているため。cpal は WASAPI の共有モードしか使わないので、
**アプリ側からこの値は動かせない**。

したがって案 A は、**Windows の設定が 48kHz のときにしか成り立たない**。

## フェーズ

| | 内容 | 完了条件 |
|---|---|---|
| **0** | `opus-rs` + `ogg` でサイン波を `.opus` にする (本体には触れない) | **プレイヤーで再生でき、長さと音程が正しい**。あわせて実機が 48kHz を出せるか確認 |
| **1** | `opus.rs` を新設。`Rendered` → Ogg/Opus のバイト列 | 48kHz の描画結果を書き出せる |
| **2** | ストリームを 48kHz 優先に (案 A)。「出力」メニューとビットレート選択 | 48/96/128/192 を選んで書き出せる |
| **3** | 検証と README・制限事項の更新 | 下記 |

**フェーズ0を先に置く理由**は VST3 のときと同じ。Ogg ヘッダの組み立てが実際に
再生できるかを、本体を触る前に確かめる。ここが通れば残りは見通しが立つ。

### 検証

- **往復で確かめる。** 書き出した `.opus` を読み戻し (`opus-rs` の `OpusDecoder`)、
  **長さが元と一致すること**と**無音でないこと**を見る。Opus は非可逆なので
  波形は比べられない
- **プリスキップの扱いが合っているか**は、先頭が欠けていないかで見る
  (デコード結果の先頭に元の音が出ていること)
- ビットレートを変えて**ファイルサイズが単調に増えること**

## 決めておくこと

- **WAV は残す** (無劣化の書き出しとして)。Opus は並べる形
- **モノラル / ステレオ以外は出せない。** Opus のチャンネルマッピングを
  真面目にやる範囲ではないので、3ch 以上のデバイスでは断る
- **書き出し中に画面が固まる**のは今までどおり (符号化のぶん少し延びる)
